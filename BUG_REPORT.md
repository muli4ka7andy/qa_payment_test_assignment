# Баг-репорт

## API-001: Ключ идемпотентности не сохраняется после fail-after-create

**Критичность:** Критическая

**Шаги воспроизведения:** Отправить корректный платёж с новым заголовком
`Idempotency-Key` и заголовком `X-Simulate: fail-after-create`. Повторить тот же
запрос без заголовка симуляции. Выполнить запрос
`/debug/payments?beneficiary_ref=<тот-же-ref>`.

**Ожидаемый результат:** Первый запрос возвращает `500`. Повторный запрос
возвращает `200` с уже созданным платежом. Количество платежей равно `1`.

**Фактический результат:** Первый запрос возвращает `500`. Повторный запрос
возвращает `201` и создаёт второй платёж. Количество платежей равно `2`.

**Риск:** Повторная отправка после таймаута может обработать платёж дважды.

## API-002: Один ключ идемпотентности принимает другое тело запроса

**Критичность:** Высокая

**Шаги воспроизведения:** Создать платёж с определённым ключом, затем повторно
отправить этот ключ с изменённой суммой.

**Ожидаемый результат:** Ответ `409`. Новый платёж не создаётся.

**Фактический результат:** Ответ `200` с исходным платежом, хотя тело запроса
отличается.

**Риск:** Клиент может получить успешный ответ для запроса с суммой, которая
отличается от фактически отправленной.

## API-003: Принимаются неположительные суммы

**Критичность:** Высокая

**Шаги воспроизведения:** Отправить корректные запросы со значениями
`amount=0` и `amount=-1`.

**Ожидаемый результат:** Ответ `422`. Платёж не создаётся.

**Фактический результат:** Для обоих значений возвращается `201` и создаётся
платёж.

**Риск:** Некорректные финансовые операции могут попасть в обработку.

## API-004: Логическое значение принимается как сумма

**Критичность:** Средняя

**Шаги воспроизведения:** Отправить корректный платёж со значением
`amount=true`.

**Ожидаемый результат:** Ответ `422`, поскольку `true` не является допустимой
денежной суммой.

**Фактический результат:** Ответ `201`, платёж создаётся.

**Риск:** Некорректное логическое значение может попасть в финансовую обработку.

## API-005: JSON null закрывает соединение без HTTP-ответа

**Критичность:** Высокая

**Шаги воспроизведения:** Отправить `null` в качестве JSON-тела с корректным
заголовком `Idempotency-Key`.

**Ожидаемый результат:** Ответ `422` с сообщением об ошибке валидации.

**Фактический результат:** Сервер закрывает соединение, не возвращая HTTP-статус.

**Риск:** Клиент получает транспортную ошибку вместо стабильного ответа API.
Это усложняет повторные запросы и диагностику.

## API-006: Пустой beneficiary_ref принимается

**Критичность:** Средняя

**Шаги воспроизведения:** Отправить корректный платёж с пустым значением
`beneficiary_ref`.

**Ожидаемый результат:** Ответ `422`. Платёж не создаётся.

**Фактический результат:** Ответ `201`, платёж создаётся с пустым
`beneficiary_ref`.

**Риск:** Платёж невозможно надёжно идентифицировать и найти через
диагностический endpoint.

## API-007: Любые изменения тела запроса игнорируются при повторе

**Критичность:** Высокая

**Шаги воспроизведения:** Создать платёж с ключом идемпотентности, затем
повторить запрос с тем же ключом, изменив `corridor`, `currency` или
`beneficiary_ref`. Отдельно повторить запрос с дополнительным полем.

**Ожидаемый результат:** Ответ `409`, новый платёж не создаётся.

**Фактический результат:** Во всех случаях возвращается `200` с исходным
платежом.

**Риск:** Сервис подтверждает запрос, параметры которого не совпадают с
переданными клиентом.

### RCN-001: Операция отсутствует у партнёра

**Критичность:** Высокая

**Идентификатор:** `R007`

**Ожидаемый результат:** Каждая операция присутствует у партнёра ровно один
раз.

**Фактический результат:** `R007` есть только у нас: `3000 USD`, статус
`success`.

**Финансовый эффект и риск:** Не подтверждены получение и расчёт операции на
`3000 USD`; операция может не попасть в расчёт с партнёром.

### RCN-002: В наших данных отсутствует операция партнёра

**Критичность:** Высокая

**Идентификатор:** `R099`

**Ожидаемый результат:** Каждая операция партнёра сопоставляется с внутренней
операцией.

**Фактический результат:** `R099` есть только у партнёра: `8000 USD`, статус
`success`.

**Финансовый эффект и риск:** Внутренняя система не учитывает `8000 USD`;
возможны потеря операции и некорректный баланс.

### RCN-003: Дублирование операции в выписке партнёра

**Критичность:** Критическая

**Идентификатор:** `R009`

**Ожидаемый результат:** Один `ref` соответствует одной записи.

**Фактический результат:** `R009` встречается дважды с одинаковыми данными:
`2500 USD`, `success`.

**Финансовый эффект и риск:** Потенциальное двойное отражение `2500 USD`,
завышение оборота или повторная выплата.

### RCN-004: Расхождение статуса операции

**Критичность:** Высокая

**Идентификатор:** `R006`

**Ожидаемый результат:** Статус согласован между системами или описано правило
перехода статусов.

**Фактический результат:** У нас `pending`, у партнёра `success`; сумма и
валюта совпадают: `30000 RUB`.

**Риск:** Возможны преждевременное зачисление, неверное резервирование или
повторная обработка операции.

### RCN-005: Расхождение суммы операции

**Критичность:** Критическая

**Идентификатор:** `R008`

**Ожидаемый результат:** Сумма и валюта совпадают.

**Фактический результат:** У нас `45000 RUB`, у партнёра `44500 RUB`.

**Финансовый эффект и риск:** Расхождение составляет `500 RUB` и напрямую
влияет на баланс и расчёт с партнёром.

### RCN-006: Систематическое расхождение дат

**Критичность:** Средняя

**Идентификаторы:** все 11 совпадающих уникальных `ref`

**Ожидаемый результат:** Даты операции в наших данных и выписке партнёра
согласованы либо однодневный сдвиг явно зафиксирован как допустимый SLA.

**Фактический результат:** Для всех совпадающих операций дата `settled_at` у
партнёра ровно на один день позже `created_at` в наших данных.

**Риск:** Если задержка в один день не предусмотрена, это может указывать на
проблему часовых поясов, неверную дату выгрузки или сдвиг расчётного периода.

**Примечание:** До подтверждения SLA расхождение считается дефектом данных
реконсиляции и требует расследования.

### Контрольные суммы

- наши данные: `385000 RUB`, `10000 USD`;
- выписка партнёра с дубликатом: `384500 RUB`, `17500 USD`.

Итоги нельзя сравнивать напрямую до исключения `R007`, `R099`, дубликата
`R009` и исправления суммы `R008`. Дополнительные `2500 USD` у партнёра
объясняются дубликатом `R009`.

### Допущения и рекомендации

- `ref` считается уникальным бизнес-идентификатором;
- дубликат `ref` считается ошибкой, если отдельное правило не разрешает
	повторные расчёты;
- суммы сравниваются только внутри одной валюты;
- до финансового закрытия нужно расследовать все шесть категорий и принять
	решение по `R006`;
- после исправления данных реконсиляцию нужно повторить и сохранить контрольные
	суммы как артефакт аудита.
